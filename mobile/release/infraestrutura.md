# Infraestrutura e domínio — Saúde em Tempo Real

Roteiro de preparação em 10/11/2026. Nenhum serviço foi contratado ou modificado por este roteiro. O nome do domínio, a titularidade das contas e as configurações de produção serão preenchidos quando confirmados.

## Caminho mais rápido para lançar

**Manter Vercel + Express + MongoDB + R2 para o primeiro lançamento**, desde que os testes de disponibilidade, privacidade, restauração e capacidade passem. O portal empacotado consulta a API HTTPS existente: leitura pública e acesso autenticado apenas nas áreas restritas. Ter o app nas lojas não exige migrar o banco nem contratar um domínio para o Supabase. Se optarmos por PostgreSQL, fazer a migração separadamente, atrás do mesmo contrato HTTPS; assim os apps não dependem de detalhes do banco.

| Componente atual | Onde fica | O que preservar |
|---|---|---|
| Site, PWA e páginas públicas | Vercel; `vercel.json`, `frontend/`, `scripts/build.js` | Site atual, caminhos dos arquivos e comportamento do PWA |
| API Express | Vercel; `api/index.js`, `backend/server.js` | Resposta pública de `GET /atendimento`; manter outros caminhos usados pelo site e pelo painel |
| Banco | MongoDB via Mongoose; `backend/db.js`, `backend/models/` | IDs, relacionamentos, horários, estados, ordenação, integridade e permissões |
| Mídia | R2; `backend/config/r2.js` | URLs que já funcionam, tipos de arquivo e separação entre mídia pública e arquivos privados |
| App das lojas | `mobile/`; portal embutido no binário | Consulta sem login, mapa, mídia, publicidade contextual, sessão dos papéis restritos, origem HTTPS da API, links públicos de privacidade/suporte e favoritos locais. |

Antes de disponibilizar o acesso restrito nas lojas, revisar a recuperação de conta com prova de titularidade, invalidar sessões ao suspender ou alterar permissões e conferir que as rotas de anúncios públicos retornam apenas dados necessários à exibição. Validar com contas fictícias em ambiente isolado; o APK de teste não modifica o backend publicado.

## Domínio e publicação do backend

- [ ] Confirmar domínio escolhido, titularidade, renovação, conta Vercel e projeto correto. O endereço provisório atual é `https://upa-tempo-guaruja.vercel.app`. O titular conclui compra, aceite e verificação quando houver autorização.
- [ ] Salvar o inventário DNS antes de alterar. Em **Settings → Domains** do projeto Vercel, adicionar o domínio escolhido e, se necessário, `www`. Escolher um canônico e redirecionar o outro. Usar os registros A/CNAME/TXT **exatos** que o painel indicar, no provedor DNS autoritativo. Preservar MX, TXT e demais registros de e-mail; não trocar nameservers sem reproduzir os registros necessários.
- [ ] Aguardar verificação de domínio e certificado. Conferir resolução, HTTPS e redirecionamento com um navegador e aparelho real, sem aceitar alertas de certificado. Ver [configuração oficial da Vercel](https://vercel.com/docs/domains/working-with-domains/add-a-domain).
- [ ] Validar página inicial, CSS, fotos, mapa, PWA, API, privacidade e suporte no domínio final. A política e o suporte precisam carregar em HTTPS, sem login e sem dados de exemplo do titular. Testar consulta pública a partir das origens efetivas das WebViews de Android/iOS; se houver ajuste de CORS, permitir apenas origens e métodos necessários, sem usar CORS como substituto de autenticação. O servidor hoje usa `cors()` globalmente.
- [ ] Definir `MOBILE_API_ORIGIN` e `MOBILE_SITE_ORIGIN` no build mobile com as origens HTTPS aprovadas; preencher `MOBILE_PRIVACY_URL` e `MOBILE_SUPPORT_URL` com páginas públicas verificadas. Seguir o [guia dos apps](../README.md) e conferir os valores no binário testado. Preferir o domínio final antes do primeiro binário público. **Manter o endereço Vercel antigo funcionando** durante a transição para builds instalados; não redirecionar a API legada sem testar versões antigas, HTTPS e CORS. Trocar a origem embutida depois do lançamento exige nova compilação; trocar o provedor do banco mantendo a mesma API não exige.
- [ ] Configurar segredos em cada ambiente pelo painel, separados entre prévia e produção: `MONGO_URI`, `JWT_SECRET` e configuração do R2 conforme os nomes usados no código. Apenas origens HTTPS públicas entram no app. Não copiar `.env`, senhas, tokens, arquivos de assinatura ou dumps para o Git. Fazer rotação de credenciais em tarefa separada e testar os efeitos sobre sessões.

**Supabase:** se usado apenas como banco atrás da API, usar a conexão gerenciada do projeto no servidor. O domínio do site fica na Vercel. A opção de [domínio personalizado no Supabase](https://supabase.com/docs/guides/platform/custom-domains) é um adicional pago para planos pagos e só entra se houver motivo para expor serviços Supabase em um subdomínio próprio. Não é requisito para o app nem substitui a migração de dados.

## Verificações antes de produção

1. **Privacidade nas respostas públicas.** Manter uma lista explícita dos campos públicos. O código analisado de `GET /areas-ads/publicas` popula o nome e o e-mail do responsável do patrocinador. Esses campos não precisam sair na API pública; antes de publicar o app com publicidade, separar a projeção pública da administrativa e verificar que toda resposta aninhada exclui esses campos, CPF, dados de usuários e outros campos internos. Revisar recursos de mapa e mídia efetivamente chamados pelo binário e registrar seus fornecedores. A equipe e os tempos desta versão são demonstrativos; não receber prontuários, nomes de pacientes ou entradas de fila individuais.
2. **Disponibilidade e dados corretos.** Testar cinco unidades, imagens, mapa, publicidade contextual, filtros, telefone/rota, exemplos identificados e estado sem rede. Medir retorno da API em aparelho, inclusive em rede móvel. Testar login, expiração de sessão, logout, permissões de funcionário e administrador, painel, edição e mídia com contas e dados fictícios em prévia separada. Não usar contas reais nas revisões das lojas.
3. **Mídia e tráfego.** Confirmar os limites reais de upload. A Vercel documenta [4,5 MB no corpo de requisição de Functions](https://vercel.com/docs/functions/limitations#request-body-size); multipart tem overhead, então limite da tela de 30 MB não vale para essa rota na Vercel. Para arquivos maiores, planejar upload direto ao storage com autorização curta, validação do objeto e confirmação antes de publicar. Para mídia de produção no R2, revisar domínio próprio, cache e limites; `r2.dev` é indicado para desenvolvimento. [Documentação de buckets públicos do R2](https://developers.cloudflare.com/r2/buckets/public-buckets/). Não copiar arquivos privados para bucket público; conservar backup separado das mídias e conferir reprodução/range dos vídeos.
4. **Backup e capacidade.** Testar restauração do banco e uma amostra de mídia em ambiente isolado. Verificar plano contratado, backup e retenção disponíveis, limites de conexões e CPU, funções, armazenamento, transferências e custo de vídeo. Definir alertas de erro/latência, orçamento e responsáveis. A consulta pública não usa autenticação; o login restrito usa o fluxo do portal. Uma futura franquia de usuários mensais do Supabase Auth é cobrança e não mede capacidade simultânea.

### Ensaio de capacidade

- Começar em ambiente isolado com dados sintéticos, limites aprovados e métricas; não disparar carga contra produção nem provedores de mapas ou mídias externas. Medir navegação normal, rajadas de abertura, atualização de lista, cache frio/quente e mistura de app/web. Usar os mesmos formatos, volume, latência e políticas previstos em produção.
- Distinguir sessões simultâneas de requisições por segundo. Exemplo: 30 mil clientes fazendo **uma** leitura por minuto, uniformemente distribuída, correspondem a **500 leituras/s** nesse endpoint antes de cache; abrir todos no mesmo instante gera uma rajada diferente. Somar as demais chamadas do site, tamanho das respostas e concorrência na função/banco. Não transformar esse cálculo em garantia.
- Priorizar leituras públicas cacheáveis com TTL curto definido conforme a atualização necessária e informação de quando foram observadas; nunca cachear endpoints privados ou respostas com dados pessoais no CDN. Tirar a inicialização/atualização dos espaços padrão do caminho de leitura pública: atualmente `GET /areas-ads/publicas` chama `garantirAreasPadrao()`. Revisar efeitos do rate limit por IP e de conexões abertas por instância sob carga.
- Definir e registrar metas de latência p95/p99, taxa de erro e custo com margem. Escalar em etapas até o alvo, registrando 429/5xx, timeouts, conexões, cache hit, CPU e tráfego. Decidir planos e capacidade só após o ensaio e revisar cada configuração cobrada.

## Migração opcional: MongoDB para Supabase

**Trocar DNS ou uma variável não migra o backend.** O código usa documentos Mongoose, `ObjectId`, populações e autenticação JWT/bcrypt próprias. Supabase usa PostgreSQL. Manter a camada Express e substituir o acesso aos dados preserva a API, sem exigir mover login, fotos e vídeos ao mesmo tempo.

| Dados atuais | Mapeamento a validar |
|---|---|
| `Atendimento` | Unidades/estado agregado e observações. Preservar ID legado, data UTC, campos de endereço, coordenadas, foto, estados e tempos. Diferenciar zero confirmado de valor desconhecido. Plantões normalizados ou JSONB validado, com acesso de acordo com a fonte. |
| `AreaAds`, `Anuncio`, `Patrocinador` | Áreas com códigos únicos, anúncios e vínculo ordenado área–anúncio; preservar períodos, formato, status, rotação, URLs e dimensões. Projeções públicas separadas de responsáveis, documentos e contatos privados. |
| `User`, `Log` | Dados administrativos em esquema restrito. Deduplicar e normalizar só com critérios aprovados; preservar papéis, bloqueios, integridade e retenção. Não importar contas/logs reais para ambientes de teste. |
| R2 e referências antigas | Manter R2 nesta migração. Inventariar chaves, URLs e mídias antigas antes de eventual troca; restaurar os objetos independentemente do banco. [Backups Supabase não incluem objetos do Storage](https://supabase.com/docs/guides/platform/backups). |

1. **Inventário e segurança.** Confirmar projeto de destino e escopo autorizado. Levantar modelos, índices, relações, dados sensíveis, referência de origem e regras de retenção. Definir metas de perda de dados e tempo de retorno aceitáveis. Fazer backup criptografado do MongoDB em local privado e testar restauração Mongo–Mongo; [`mongodump`](https://www.mongodb.com/docs/database-tools/mongodump/) gera BSON de backup, não SQL para importar no PostgreSQL.
2. **Ambiente de ensaio.** Usar dados sintéticos e banco local ou projeto de teste isolado. Fixar versão das ferramentas e consultar `--help`: desde a [CLI Supabase v3](https://supabase.com/changelog/supabase-cli-v3), o alvo padrão é local e operações hospedadas devem indicar o alvo remoto. Criar migrações SQL versionadas e comparar restrições, chaves estrangeiras, unicidade, índices, carimbos de data e precisão. Criar roteiro de importação idempotente com relatório de rejeições sem dados pessoais em logs. Preservar IDs antigos no contrato HTTPS; se houver UUID novo, manter associação estável e vínculos.
3. **Conexão e autorização.** Manter banco em esquema não exposto à Data API se o acesso for só por Express. Usar credencial de privilégio mínimo e TLS; para Functions avaliar [pooler em modo transação](https://supabase.com/docs/guides/database/connecting-to-postgres), pool pequeno e driver compatível com as limitações do modo, incluindo prepared statements. Se alguma tabela for exposta pela Data API, habilitar RLS e grants mínimos, com testes de isolamento entre usuários e de acesso anônimo. Chaves de serviço jamais no app. [Proteção da Data API](https://supabase.com/docs/guides/api/securing-your-api).
4. **Compatibilidade.** Manter autenticação Express durante a primeira troca, com hash e papéis protegidos, ou adiar a migração administrativa inteira. Supabase Auth é um projeto separado: conferir compatibilidade de importação de hashes, redefinição segura e transição de sessão, sem copiar senhas em claro ou confiar em papéis definidos pelo cliente. Testar login e bloqueio no painel, validade de sessão e autorizações de escrita. Confirmar paridade do JSON público, erros, headers, filtros, ordenação, mídia e app já instalado.
5. **Virada controlada.** Combinar janela, congelar escritas ou importar um delta verificável, salvar último snapshot e inventário de mídia. Importar, conciliar contagens/IDs/relações/datas e hashes de amostras não sensíveis, validar leitura e escrita antes de reabrir. Mudar somente a configuração do backend de produção quando os testes passarem; manter API e domínio estáveis. Não apagar MongoDB ou mídia antiga.
6. **Retorno.** Se a API, painel, autorização ou tempos divergirem, pausar escritas, preservar as alterações feitas desde a virada, reconciliar com o MongoDB e restaurar a versão/configuração anterior. Validar API pública, administração e mídia após o retorno. Evitar apontar duas versões para bancos graváveis sem estratégia de sincronização. Só encerrar o provedor antigo após período de observação e restauração conferida.
